**Theme:** PostgreSQL authoritative command/outbox publication barrier

## Problem closed in this pass

Before this pass, the PostgreSQL mutation writer committed `command_journal` and `outbox_events` before the runtime checkpoint/normalized projections were committed. The outbox publisher was therefore technically able to publish an event during the window where the corresponding authoritative state checkpoint had not yet succeeded. Pass 10 made retries durable, but it did not close this outbox/state ordering window.

## Implemented

- Added `AuthoritativeCommandGate` for PostgreSQL authoritative mutations/checkpoints on a node.
- Added ambient per-command durability batch IDs and attached them to every mutation generated by a PostgreSQL HTTP command.
- `OperationalMutationBuffer` now tracks pending authoritative batches, committed batches and abandoned/rejected batches.
- Added durability-batch and `authoritative_committed_at_utc` metadata to PostgreSQL command journal/outbox rows.
- `PostgreSqlOutboxPublisherService` now ignores every row until `authoritative_committed_at_utc` is set.
- `StatePersistenceService` now performs the authoritative barrier inside the same PostgreSQL transaction that writes:
  - runtime checkpoint;
  - normalized projections;
  - durable idempotency projection;
  - authoritative-commit markers for eligible journal/outbox rows.
- Periodic PostgreSQL checkpointing uses the same command gate, preventing a timer checkpoint from observing a half-completed HTTP command on the node.
- PostgreSQL API mutation error/exception handling captures a pre-command in-memory snapshot, restores it when the command is rejected/fails before durability acknowledgement, and abandons the batch so failed work cannot become publishable.
- `/health/ready` now considers pending authoritative batches.
- Primary-only `DispatchDeliveryWorker` completion mutations and `AlertEscalationWorker` escalation mutations use the same PostgreSQL gate and durable checkpoint boundary.
- Added migration `013_authoritative_outbox_barrier.sql` with upgrade backfill for existing rows.

## Remaining hardening

This is a publication-safety barrier, not a claim that DISRoute has already replaced all in-process command stores with relational command handlers. The next database hardening step is live PostgreSQL integration testing followed by moving safety-significant command state changes themselves into explicit normalized relational transactions with the idempotency receipt, journal and outbox written directly in that transaction. Real replication/promotion/PITR/network-partition/geographic-DR qualification remains separate infrastructure work.
